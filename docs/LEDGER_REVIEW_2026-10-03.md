# ความเห็นต่อปัญหา change_ledger (เกณฑ์ t > 7.93)

ตอบคำถามจาก session บนเครื่องผู้ใช้ (3 ต.ค. 2026) เอกสารนี้เป็นความเห็นอย่างเดียว ยังไม่ได้แก้ `research/change_ledger.py` หรือ `change_ledger.json`

**สรุป:** เห็นด้วยกับการแยก 3 ประเภท (A edge / B risk / C fidelity) แต่ถ้าทำตามที่เขียนไว้ตรงๆ จะเกิดช่องโหว่ 7 จุด (ข้อ 3) ต้องปิดให้ครบก่อน implement ช่องที่ใหญ่ที่สุดคือข้อ 3.2 เมื่อแยก family แล้ว family เล็กจะได้ floor ต่ำกว่า t = 2

## 1. ปัญหาจริงใหญ่กว่า "k สูงเกิน"

ตัวเลขทั้งหมดในหัวข้อนี้วัดจาก `change_ledger.json` บน branch นี้ ซึ่งมี 54 รายการ ยังไม่มีรายการเรื่อง lot rounding ที่ทำบนเครื่องผู้ใช้

1. **ledger บอกว่านับ "on this setup" แต่จริงๆ นับรวมทั้งโปรเจกต์เป็นก้อนเดียว**
   - k = 15,002,017 รวมทุกอย่างไว้ด้วยกัน: EURUSD reversal, NFP, USDSEK, vendor families และการค้นหารูปแบบเพื่อแทนที่ระบบอีก 15 ล้านแบบ
   - ไม่มีรายการไหนเลยที่เป็นการแก้ G27K
   - ข้อเท็จจริงที่น่ากังวลกว่าคือ การแก้ G27K ทุกอย่างถูกรวมอยู่ใน k ก้อนนี้ แต่ grid 27,648 แบบที่เลือก G27K #1 ออกมากลับ**ไม่อยู่ใน ledger เลย**

2. **verdict ใน ledger ไม่ตรงกับการตัดสินใจจริงแล้ว**
   - `g27k_b_1pct_brake` ผ่านเกณฑ์ที่ตัวเองประกาศไว้ 3 จาก 4 ข้อ
   - `g27k_fourth_market_walkforward` ผ่านเกณฑ์ที่ประกาศไว้
   - ทั้งสองรายการถูกประทับว่า INCONCLUSIVE เพราะไม่ผ่าน t floor แต่ระบบที่ส่งมอบคือ 4 ตลาด + เบรก ซึ่งก็คือสองเรื่องนี้
   - เมื่อ verdict ไม่มีผลต่อการตัดสินใจ ledger ก็หมดอำนาจไปแล้ว ซึ่งอันตรายกว่าการที่ floor สูง

3. **floor 7.93 สูงกว่าหลักฐานของตัวระบบเอง**
   - G27K #1 ทั้ง 1,497 ไม้ใน `handoff_expected_trades_h4_00utc.json` มี mean +0.368R, sd 3.25 จึงได้ t ≈ 4.4
   - floor ปัจจุบันจึงเท่ากับขอให้ "การเปลี่ยนแปลง" มีหลักฐานแรงเกือบ 2 เท่าของ "ตัวระบบ"
   - ระบบเองไม่ได้ผ่านเข้ามาด้วย floor นี้ แต่ผ่านด้วย walk-forward, OOS 2024–26 และ drift placebo

4. **อีกด้านหนึ่ง `floor_for` ไม่ใช่เกณฑ์นัยสำคัญ แต่เป็นค่าคาดหมายของค่าสูงสุดจาก k ตัว**

   | k | floor (σ = 1.475) | floor (σ = 1) |
   |---|---|---|
   | 1–2 | 0.77 | 0.52 |
   | 10 | 2.32 | 1.57 |
   | 100 | 3.73 | 2.53 |
   | 27,648 | 6.05 | 4.10 |
   | 15,002,017 | 7.93 | — |

   ถ้าแยก family แล้วใช้สูตรเดิม family ที่มี 1–10 รายการจะผ่านได้ที่ t < 1 ถึง 2.3 ซึ่งเปิดประตู p-hacking กว้างกว่าเดิม

## 2. ตอบ 3 คำถาม

**Q1 — ledger ควรครอบคลุมกฎขนาดไม้หรือไม่**

ควรครอบคลุม แต่ไม่ใช่ด้วย t-test ต่อไม้ ซึ่งใช้ไม่ได้กับเรื่องนี้จริงตามที่ว่า อย่างไรก็ตาม ประโยค "sizing เปลี่ยน E(R) ไม่ได้" จริงแค่บางส่วน:

- **ขนาดที่ขึ้นกับสถานะบัญชีเท่านั้น** (% คงที่ เบรก DD การปัด lot) จะไม่เปลี่ยนว่าเข้าไม้ไหน ถ้า R ของแต่ละไม้เป็นอิสระต่อกัน กฎแบบนี้เพิ่มผลตอบแทนต่อความเสี่ยงที่คาดหวังไม่ได้
  - ถ้า backtest ออกมาดีกว่า แปลว่าโชคดีกับเส้นทางในอดีตเส้นเดียว หรือ R มี autocorrelation
  - การเลือกจึงเป็นเรื่องรสนิยมความเสี่ยง ไม่ใช่เรื่องสถิติ → **ประเภท B**
- **ขนาดที่ขึ้นกับตัวแปรตลาด** เช่น ATR percentile, ข่าว หรือผล 8 ไม้ล่าสุดของตลาด (คือ AI monitor) เป็นตัวกรองแบบนุ่ม เพราะให้น้ำหนักไม้ตามสิ่งที่อาจทำนาย R ได้ → **ประเภท A**
- **ขนาดที่กลายเป็น 0** เช่น lot ต่ำกว่า min lot หรือข้ามไม้เพราะ open risk เกิน 6% ทำให้ชุดไม้เปลี่ยน → **ประเภท A** สำหรับไม้เหล่านั้น

**Q2 — multiplicity ควรคิดภายใน family หรือตลอดชีพ**

ควรคิดภายใน family ที่ผลิตผู้สมัครนั้น:

- การค้น 15 ล้านแบบหา "ระบบแทนที่" และไม่ได้ผลิตกฎปัด lot ดังนั้นกฎปัด lot ไม่ได้รับ max-of-k ของการค้นนั้นมา
- แต่ family ต้อง**ไม่เริ่มที่ 0** family "แก้ edge ของ G27K" ต้องเริ่มที่ k = 27,648 คือ grid ที่เลือก G27K มา ซึ่งได้ floor 6.05 (σ = 1.475)
- ถ้าวันหน้ามีผู้สมัครที่มาจากผลของการค้น 15 ล้านแบบ (เช่น เอารูปแบบที่ชนะในการค้นนั้นมาต่อกับ G27K) ผู้สมัครนั้นต้องใช้ k ของการค้นนั้น

## 3. ช่องโหว่ในข้อเสนอ และวิธีปิด

**3.1 Family shopping** (ตั้ง family ใหม่เพื่อหนี k)
- เก็บ family เป็นรายการตายตัวในโค้ด (`FAMILIES`)
- `register` ต้องระบุ family ที่มีอยู่แล้วเท่านั้น
- การสร้าง family ใหม่ต้องเป็น commit แยก มีเหตุผล และเกิดก่อน register รายการแรกของ family นั้น
- k ภายใน family ไม่รีเซ็ต

**3.2 Floor ต่ำเกินใน family เล็ก**
- ใช้ `floor = max(expected_max_t(base_k + k_family, 1.475), 3.0)`
- 3.0 เป็นเกณฑ์ขั้นต่ำสำหรับงานที่ข้อมูลถูกใช้ซ้ำมามาก (Harvey, Liu & Zhu 2016)

**3.3 ติดป้ายผิด** (เอา A มาใส่เป็น B หรือ C เพื่อเลี่ยงการทดสอบ)
- ห้ามให้ผู้ลงทะเบียนเป็นคนเลือกประเภทเอง ให้ ledger ตัดสินเชิงกลไก
- `record` รับไฟล์ไม้ของ baseline และ variant แล้ว diff `(market, entry_time, exit_time)`
- ไม้ต่างกันแม้แต่ไม้เดียว (รวมถึงไม้ที่ size เป็น 0) → A
- ไม้เหมือนกันทุกไม้ ต่างแค่ size → B แต่ถ้าตัวคูณ size อ่านตัวแปรตลาด → A
- ไม้และ size ตามที่ตั้งใจเหมือนเดิม ต่างแค่โมเดลต้นทุน ราคาเติม หรือการปัด → C

**3.4 B ตัดสินจากเส้นทางจริงเส้นเดียว** (ซึ่งคือการ overfit กับลำดับเหตุการณ์ในอดีต)
- (a) ประกาศเพดานก่อนดูผล เช่น
  - MC P(DD > 50%) ≤ 5%
  - DD p95 ≤ X
  - margin level ต่ำสุด ≥ Y
  - ทุกไม้มี lot ≥ min lot ที่ทุนเริ่มต้นตามแผน
- (b) ประเมินบน bootstrap ไม่ใช่เส้นทางจริงอย่างเดียว ใช้ iid เพื่อตัด autocorrelation และใช้ block 6 เดือนเพื่อดูความรุนแรง
- (c) ประกาศ "ตัวเลือกหลัก" ไว้ก่อน ถ้ามีหลายตัวที่ผ่านเพดาน ให้ใช้ตัวเลือกหลัก ไม่ใช่ตัวที่ CAGR หรือ MAR สูงสุด
- (d) ยังต้องนับจำนวนตัวเลือกที่ดู เพื่อความโปร่งใส แต่ไม่ใช้คิด floor
- (e) verdict เป็น `ADOPTED_BY_USER` หรือ `NOT_ADOPTED` พร้อมวันที่ ไม่ใช่ INCONCLUSIVE

**3.5 ใช้ C เป็นประตูหลัง** (เลือกโมเดลต้นทุนหรือ slippage ที่ทำให้ผลดีขึ้น)
- ต้องมีแหล่งความจริงภายนอก เช่น สเปกโบรก tick จริง หรือ fill จริงจาก MT5 พร้อมไฟล์และ hash บันทึกตอน register
- **รับเข้าไม่ว่าผลจะดีขึ้นหรือแย่ลง** (สมมาตร) C ที่ทำให้ผลแย่ลงแล้วถูกปฏิเสธถือว่าผิดกฎ
- ค่าพารามิเตอร์ fidelity มาจากการวัด ห้าม sweep หาค่า
- มี regression test: ปิดตัวเลือก C แล้วต้องได้ตัวเลขเดิม เช่น fractional ได้ 28.1% / DD 32.3%

**3.6 "A ต้องยืนยันด้วย forward เท่านั้น"** — เห็นด้วย แต่ต้องรู้ว่าแทบจะไม่มีทางผ่าน
- sd ของ R = 3.25 และมีประมาณ 88 ไม้ต่อปี
- ผลต่าง 0.1R ต้องใช้ข้อมูลประมาณ 48 ปีจึงได้ t = 2 (เทียบแบบไม่จับคู่)
- ผลต่าง 0.2R ต้องใช้ประมาณ 12 ปี
- ทางที่ทำได้จริงคือ **paired test เฉพาะไม้ที่ต่างกัน** ตัวอย่างสำหรับตัวกรอง: ทดสอบว่า mean R ของไม้ที่ถูกตัดออกน้อยกว่า 0 หรือไม่ วิธีนี้มี power สูงกว่ามาก
- ต้องประกาศล่วงหน้า: วันเริ่ม จำนวนไม้ขั้นต่ำ สถิติที่ใช้ และ sequential boundary เช่น O'Brien–Fleming
- การแอบดูผลระหว่างทางโดยไม่มี boundary คือ p-hacking อีกแบบ
- ข้อสรุปที่ควรเขียนให้ชัด: การแก้ edge ที่คาดว่าให้ผลต่างน้อยกว่า 0.2R ต่อไม้ **พิสูจน์ไม่ได้ในชั่วชีวิตของระบบ จึงไม่ควรทำ**

**3.7 ย้อนเปลี่ยน verdict เก่า**
- ห้าม re-judge รายการเก่าด้วยกฎใหม่จนเปลี่ยน verdict
- ทำ migration ครั้งเดียว: เพิ่ม `family` และ `class` ให้รายการเก่า โดยเก็บตาราง mapping ทั้งหมดไว้ในไฟล์เดียว และคง verdict เดิมไว้
- ถ้าต้องการใช้กฎใหม่กับเรื่องเดิม ให้ register ใหม่ด้วย id ใหม่

## 4. กรณี `g27k_lot_rounding_nearest`

- **ส่วนที่เป็น C (ต้องรับเข้าเลย):** ให้การจำลองใช้ lot step และ min lot จริงของ Exness
  - ตัวเลขที่ควรรายงานจากนี้คือ round-down 26.8% / DD 31.0% ไม่ใช่ 28.1% ของ fractional
  - ต้องนับด้วยว่ามีไม้ที่ปัดแล้ว lot เป็น 0 กี่ไม้ เพราะไม้พวกนั้นทำให้เกิดผลแบบ A
- **ส่วนที่เป็น B (ผู้ใช้เลือก):** วิธีปัด
  - round-to-nearest เฉลี่ยได้ 0.93% แต่บางไม้จะเสี่ยงเกิน 1%
  - ตัวเลือกที่ปลอดภัยกว่าคือ ปัดใกล้เคียงแต่ไม่เกิน 1.25% ของบัญชี หรือปัดลงโดยตั้งเป้าที่ 1.07% ให้เฉลี่ยออกมาประมาณ 1%
  - ทุกตัวเลือกเปลี่ยนแค่ size จึงไม่ต้องผ่าน t
- ส่วนต่าง 26.8% กับ 27.7% ต่อปีเท่ากับขยับ risk จาก 0.89% เป็น 0.93% เป็นเรื่องขนาดความเสี่ยง ไม่ใช่ edge
- ภายใต้กฎใหม่ verdict ควรเป็น `ADOPTED_BY_USER` หรือ `NOT_ADOPTED` ไม่ใช่ INCONCLUSIVE

## 5. ร่างสำหรับ implement (`research/change_ledger.py`)

```
FAMILIES = {
  "legacy_project":     dict(base_k=0),      # ทุกรายการก่อน 2026-10-02 ที่ไม่ใช่ g27k_*
  "replacement_search": dict(base_k=0),      # 3 การค้นใหญ่ + per_market_* + multi_market_* + macro_only
  "g27k_edge":          dict(base_k=27648, history_exhausted=True),
  "g27k_risk":          dict(),              # B: ไม่มี floor
  "fidelity":           dict(),              # C: ไม่มี floor
}
MIN_T = 3.0

register: --family (ต้องมีอยู่ใน FAMILIES)
          B: --limits JSON, --primary
          C: --source <ไฟล์หรือ URL> (บันทึก sha256)
record:   --baseline-trades, --variant-trades -> classify() ตัดสินประเภทเอง (ข้อ 3.3)
          A: floor = max(expected_max_t(base_k + k_family, 1.475), MIN_T)
             family ที่ history_exhausted -> รับเฉพาะผลที่ test_period เริ่มหลังวัน register (forward)
          B: --limits-result JSON + --user-decision -> ADOPTED_BY_USER / NOT_ADOPTED
          C: --regression-ok -> ADOPTED (ไม่ดูทิศทางของผล)
status:   แสดง k และ floor ของแต่ละ family และแสดง global k ไว้ดูประกอบ
tests:    classify() กับ 3 กรณี; family เล็กต้องได้ floor >= 3.0;
          family ที่ history_exhausted ต้องปฏิเสธ test_period ที่เริ่มก่อนวัน register
```
